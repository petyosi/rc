# PRP Generation

Generate an implementation-ready PRP from a bounded feature request.

## Process

0. Before reconnaissance, inspect active context when the host exposes it. If it is already around 45% of the window, or roughly 100,000-120,000 input tokens when the window is unknown, create a compact decision checkpoint and compact or hand generation to one fresh-context generation worker with no inherited conversation history. Keep that worker read-only for repository source; it may return or write only the PRP artifact. Pass only the request, settled decisions, current workspace and baseline, relevant artifact paths, and required output contract. Do not compact a short context by habit: compaction adds latency and can discard useful nuance. When the host does not expose context usage, compact only after a long multi-turn thread, a prior implementation/review cycle, or evidence that the current prompt is carrying substantial unrelated history.
1. Run main-agent reconnaissance in the research workflow's three evidence waves: instructions, exact stack versions, relevant structure and intent docs, canonical analogue, public boundary, validation commands, recent relevant history, current commit, and working-tree state. Batch independent reads and stop when the uncertainty ledger has no load-bearing gap.
2. Reapply the Planning Router and select Quick, Standard, or Deep assurance. Switch to Roadmapping if reconnaissance reveals dependent outcomes or distinct validation loops.
3. Research according to the chosen profile:
   - Quick: main agent inspects the closest analogue, direct integration points, representative consumer path, and targeted tests.
   - Standard: combine implementation path and consumer/blast-radius research into one lane. Delegate only when it usefully reduces uncertainty. Launch external research only for version-sensitive external contracts.
   - Deep: use separate implementation and consumer/verification lanes only when their evidence surfaces are genuinely independent; launch external research only for version-sensitive external contracts.
4. Vet all load-bearing claims that affect scope, tasks, public behavior, schema, security, compatibility, or validation. For Standard supporting details, verify the cited exemplar and sample additional claims when needed; do not mechanically reopen every non-contested citation.
5. Classify material unknowns as further research, spike, user decision, reversible execution detail, or accepted risk. Defer reversible local details. Run a spike only when observation could change architecture, scope, public contracts, decomposition, or validation strategy. When the uncertainty ledger closes, capture one compact decision snapshot—profile, settled choices, task/consumer mapping, validation surfaces, and remaining accepted risks—and draft immediately from it. Do not continue broad design exploration or reopen settled evidence while drafting.
6. Clarify only consequential product, policy, scope, or technical choices that evidence cannot resolve. Use the clarification mode.
7. Capture the final baseline after spike cleanup: commit, working-tree status, and overlapping user changes.
8. Generate the PRP from the template. Use `CX-N` scenarios as the sole observable contract and reference those IDs from tasks. Omit inapplicable and empty optional sections. For Standard, target about 300 lines and 24 KiB; treat 400 lines or 32 KiB as an exceptional ceiling whose load-bearing reason must be named in the Assurance rationale. Prefer workspace-relative validation commands. Every public input that can change routing or behavior—filters, selectors, environments, modes, versions, and compatibility variants—must appear in the relevant scenario, task, or explicit out-of-scope statement. Do not use hedges such as "where practical" or "if feasible" for evidence required by a `CX-N` scenario; define a deterministic exercise, an explicit conditional gate, or an unavailable prerequisite. For every composite gate that combines independently meaningful setup, build, package, install, service, browser, or external-check phases, record one final integrated command plus a focused diagnostic command or phase selector for each expensive phase. Also name success and failure terminal signals, progress visibility, and cleanup ownership for processes, ports, sessions, and scratch state. If safe phase isolation is impossible, state why and give the cheapest failure-local diagnosis path.
9. Run `python3 <skill-directory>/scripts/validate_prp.py --workspace <current-workspace> <prp-path>` from the current workspace before semantic review. Fix structural and workspace errors. Treat compactness and evidence-language warnings as prompts to remove repetition or ambiguity, not as permission to delete necessary contracts. Self-review the public entry point against the PRP's complete input surface, then use the validator, `git diff --check`, counts, and small targeted searches or line ranges; do not dump the whole artifact, a broad keyword match, or complete successful command output back into context.
10. Cold-review only when required by the profile:
   - Quick: skip.
   - Standard: use one bounded contract audit only when self-review records a named semantic risk, confidence is below 8/10, the plan changes a nontrivial public contract that existing tests do not characterize, or the exceptional size ceiling is approached. This is not a general repository review. Give the auditor the PRP, baseline, decision snapshot, exact trigger, and already-vetted citations. Limit it to the PRP plus at most two evidence waves and normally no more than 6-8 tool calls. It may inspect only live surfaces needed to test the trigger, workspace/baseline correctness, the complete public input surface, deterministic evidence for each `CX-N`, and scenario-to-task-to-validation coverage. It must not reread the skill, template, unrelated history, older PRPs, or already-vetted external versions unless the trigger specifically contests them. Require blockers and important findings only, capped at roughly 1,500 tokens.
   - Deep: use one fresh-context read-only cold reviewer for evidence traceability, scenario/task coverage, testability, scope expansion, and applicable runtime/public/test/documentation/release surfaces when self-review leaves a concrete high-risk question or the plan changes a high-impact boundary. Mark irrelevant surfaces `N/A` rather than returning early.
   Give any reviewer the PRP, parent contract when applicable, repository baseline, and focused review criteria with no inherited conversation history.
   Complete the main-agent self-review before launching the reviewer. While it runs, do not spend full-context turns polling or duplicating its work. Prefer a notification-driven wait that needs no polling. Otherwise use the longest wait permitted by the host's communication cadence—normally 45-60 seconds in an interactive session—and do not call status/list tools before it expires. After a timeout, inspect status once only when it changes the next action; otherwise start another longest-permitted wait.
   After confirmed findings, revise and reproduce them in the main agent. Do not launch a general second cold review. Use one targeted follow-up, preferably with the same reviewer, only when a specific contract remains unresolved, validation fails, or the revision materially changes decomposition, public schema/API behavior, security, migration/rollback semantics, or the evidence strategy. Give that follow-up the original findings plus the revision diff and exact changed ranges; require it to inspect the diff and cited context only, reopening the whole artifact only when the diff invalidates surrounding contracts. Cap the targeted response at roughly 2,000 tokens. Otherwise finish with targeted self-review and validation.
11. Rerun the PRP validator after review revisions, then finalize the artifact at `plans/{XXX}-{feature-name}.md`, auto-incrementing the number. Keep the slug lowercase, hyphenated, and at most 50 characters.
12. For a roadmap child, link the PRP, baseline, and discoveries back to the parent and set the step to `PRP READY`.
13. Report assurance profile, research coverage, consumer evidence readiness, spike outcomes, validation baseline, confidence, and remaining risks.

## Generation Efficiency

- Around 45% of the context window, or roughly 100,000-120,000 input tokens when the window is unknown, create a compact generation checkpoint containing the baseline, assurance profile, decision snapshot, vetted load-bearing citations, artifact path and validator state, unresolved review findings, and remaining edits. Prefer host compaction before cold review or a substantial revision. If compaction is unavailable, continue only from the checkpoint with bounded reads and no renewed repository tour. This is a threshold, not a recommendation to run `/compact` before every PRP.
- Avoid model turns whose only purpose is progress polling. A delegated completion notification or the smallest number of longest-permitted waits owns the idle interval.
- Preserve review quality by reducing orchestration and duplicated evidence, not by skipping a required reviewer, consumer scenario, or validation surface.

## Finalization Gate

Do not call a PRP implementation-ready while a high-impact empirical assumption remains unresolved unless the user explicitly accepts the risk and the PRP contains a safe conditional gate. Every observable promise needs an achievable evidence surface. Create a standalone spike PRP when the required experiment is itself substantial.
