# PRP Execution

Implement one PRP in the current workspace. Never execute a roadmap wholesale.

## Process

0. Before loading the PRP or starting broad preflight, inspect active request context when the host exposes it. If it is already around 45% of the window, or roughly 100,000-120,000 input tokens when the window is unknown, do not begin implementation in that context. Create a compact handoff and compact or start one fresh-context writer with no inherited conversation history; pass only the PRP, parent-step summary when applicable, baseline/status, preserved user changes, exact relevant paths, and validation commands. Do not compact or hand off a short context by habit; preserve concise decision history when it fits comfortably. When usage is unavailable, use a deterministic fallback: checkpoint after two substantial completed milestones, or before the first outside-in/integrated validation phase when reconnaissance, implementation, and focused gates have already occurred. If substantial work remains, compact or hand off then instead of carrying the entire execution transcript forward.
1. Read the PRP completely. Extract the assurance profile, success criteria, `CX-N` scenarios, expected changes, exclusions, task gates, final validation, risks, and pause conditions. For a child, confirm parent dependencies and inherited contracts still match the live repository.
2. Run preflight: capture commit, status, relevant diff, and pre-existing user changes; re-read key implementation files; confirm planned paths, symbols, and assumptions. Use noninteractive, read-only discovery commands and direct installed binaries; do not use a version probe or status command that can install, update, repair, or prompt. Update the PRP if material drift invalidates it.
3. Review only when the profile and live drift require it: skip Quick. Under Standard, skip preflight review when the PRP has a current generation audit and its baseline and contracts still match. Otherwise use one bounded contract audit only when a low-confidence or long-lived PRP plus preflight evidence exposes a named semantic risk. Pass the PRP, current baseline, exact trigger, and already-vetted citations without conversation history; limit the audit to at most two evidence waves, normally 6-8 tool calls, and roughly 1,500 output tokens. Do not reread the skill, template, unrelated history, older PRPs, or settled external versions. Under Deep, use one fresh-context read-only reviewer only when the PRP lacks an equivalent current review and preflight exposes a concrete high-risk question. After fixes, use a targeted follow-up only for a specific unresolved contract or failed validation; do not repeat a general review.
4. Create a task list. For a child, mark the roadmap and step `ACTIVE` / `IN PROGRESS` immediately before the first source edit.
5. Implement in dependency order using coherent milestones. Preserve `CX-N` traceability and supported documentation/examples. For each milestone, gather the required evidence once, apply related edits together, and run its focused gate. Batch independent reads and avoid rereading unchanged PRP sections or source. Normally use one discovery/read round and one edit round; every additional round must answer a named unresolved question or a concrete failure.
6. Validate with single ownership:
   - Run a focused gate after a task that changes a public contract, schema, security boundary, migration state, concurrency behavior, or prerequisite for later tasks.
   - For ordinary tasks, validate at coherent milestones rather than after every edit.
   - Run the integrated final suite once after implementation. Do not rerun an unchanged passing suite merely to give another phase ownership of it.
   - Maintain a compact validation ledger containing each passing gate and the files, generated artifacts, runtime state, or environment assumptions that can invalidate it. After a later edit, rerun only gates whose recorded inputs changed. Formatting, test-only, documentation, or PR-metadata changes do not invalidate unrelated backend, frontend, build, or outside-in gates.
7. Record only actual scope expansions, deviations, or unresolved risks. Do not create empty Execution Notes boilerplate. Pause when expansion crosses a shared invariant.
8. Self-review every implementation hunk and changed test against the PRP. Confirm each `CX-N` scenario has an executable outside-in procedure.
9. Validate the PRP for structural and workspace errors, but treat generation compactness warnings as non-actionable after execution. Never delete research, decisions, risks, validation evidence, or execution notes to make an executed PRP meet generation size targets. Report modified files, focused and final validation evidence, scope changes, deviations, and unresolved risks. Leave the child `IN PROGRESS` and report `IMPLEMENTED — VERIFICATION PENDING`; do not append a Verification Record, mark the child `VERIFIED`, or unblock downstream work. Verification mode exclusively owns those actions. Planning cold review and execution self-review are inputs to verification, never substitutes for it. If the request also asks for verification, read `mode-verification.md`, `consumer-contract.md`, and the PRP before starting verification; do not improvise verification inside execution mode.

## Execution Efficiency

- Prefer targeted `rg`, bounded file slices, and concise status commands. Default individual tool output to at most 4,000 tokens and successful test/build output to at most 2,000 tokens; raise a limit only for a named need. Store full logs outside the conversation and surface summaries or failure-local excerpts. Do not concatenate broad file dumps, carry complete successful logs, or repeatedly dump whole files into context. If output truncates, stop and replace the query with narrower searches or slices instead of following it with another broad read.
- After a patch-context mismatch, reread the exact region once and combine the remaining related changes into one corrected patch. Do not retry guessed hunks.
- Use the cheapest representative gate while iterating. After a final-suite failure, run only the failing or affected gate until it passes, then rerun the integrated suite once. Do not alternate full suites with small edits.
- Report progress at milestone boundaries, not between independent reads or mechanical edits. Batch work that can run safely together. At every milestone boundary, recheck active request context when exposed; if it has crossed the checkpoint threshold and substantial work remains, checkpoint and compact or hand off before the next discovery/edit round.
- Monitor request context when the host exposes it. Around 45% of the context window, or roughly 100,000-120,000 input tokens when the window is unknown, stop broad exploration and create a compact execution checkpoint containing: baseline and preserved user changes, completed milestones, files changed, remaining tasks, current failures, validation evidence, and active processes.
- Prefer host compaction at that checkpoint. If compaction is unavailable and the next milestone requires substantial reading or editing, hand the remaining execution to one fresh-context writer with no inherited conversation history. Pass only the PRP, parent-step summary when applicable, checkpoint, exact relevant paths, and validation commands. The prior writer must stop editing; the new writer must confirm status and the last milestone gate before continuing. Never hand off mid-patch or with an unexplained active test/dev process. If neither compaction nor a fresh writer is available, continue from the checkpoint with targeted reads only and refresh it at the next milestone.
- For a yielded command expected to run longer than five seconds, wait 10-30 seconds on the existing session before polling again; use the longest interval consistent with the command's normal duration and the host's communication cadence. Never use repeated one-second polls for tests, builds, installs, hooks, or browser harnesses. Poll sooner only when the process is interactive or documents a sub-five-second failure signal. A silent poll is not a new diagnostic turn.
- Keep research/review agents read-only. A sequential execution handoff changes writer ownership; it never permits concurrent source writers.

## Composite Gates and Long-Running Processes

- Treat a gate as composite when it combines independently meaningful setup, build, package, install, service, browser, or external-check phases, or when repeating successful setup materially dominates diagnosis time. Before the first integrated run, identify the PRP's focused diagnostic command or phase selector for every expensive phase. If one is missing, add the smallest safe selector or record the direct underlying command before using the integrated gate as a debugging loop.
- During iteration, run only the failing phase until it passes. Reuse scratch clones, installed dependencies, caches, or built artifacts only when doing so cannot hide the failure or invalidate the final evidence. Then run the clean source-of-truth integrated gate once. Never repeatedly replay earlier passing phases merely to reach a known late failure.
- Require every harness-started process to expose observable success and failure terminal states, lightweight phase progress, and `finally`-style cleanup for process groups, browser sessions, listeners/ports, and temporary state. A failure state must terminate its wait immediately; do not wait only for success.
- When a process is unexpectedly silent beyond its documented phase behavior, inspect the active process, child state, terminal state, and owned ports/sessions once before waiting again. Do not use repeated blind polling as diagnosis. Before any retry or handoff, confirm that the prior attempt's owned processes, listeners, sessions, and secret-bearing scratch state are gone.

## Resumption

Read the PRP, latest execution checkpoint or Execution Notes, task state, and git status. Reconstruct the preflight baseline and verify the last completed milestone before continuing.
